# 多人共享菜单微信小程序设计文档

## 1. 项目定位

本项目是一个面向朋友、小圈子或多人协作场景的微信小程序，用于创建独立空间、上传菜品、多人共同选择菜品，并由厨师确认可做情况后生成最终菜单与虚拟金额汇总。

项目不是传统餐饮外卖系统，第一阶段也不接入微信支付。菜品价格使用虚拟货币，仅用于空间内记账、娱乐或内部结算。

核心定位：

- 多个空间共享同一个小程序。
- 每个空间的数据相互独立。
- 空间成员都可以上传菜品。
- 多个点单局可以同时存在。
- 成员共同往同一个点单局里添加菜品。
- 厨师确认菜品是否可做、能做多少份。
- 系统根据厨师确认结果自动计算最终有效份数和虚拟金额。

## 2. 用户角色

### 2.1 普通成员 member

普通成员是空间里的基础用户。

权限：

- 加入空间。
- 浏览空间菜品。
- 上传菜品。
- 创建点单局。
- 往点单局中添加菜品。
- 修改或删除自己添加的菜品份数。
- 查看点单局汇总、最终订单和历史记录。

限制：

- 不能修改别人的点单份数。
- 不能修改厨师确认结果。
- 不能管理空间成员角色。

### 2.2 厨师 chef

厨师是空间中负责确认菜品供应情况的成员。

权限：

- 拥有普通成员的全部权限。
- 查看点单局完整菜单。
- 确认某道菜可做、部分可做或无货。
- 设置某道菜最终可做份数。
- 填写厨师备注。
- 触发或更新厨师确认结果。

限制：

- 厨师不直接修改成员各自原始点单份数。
- 当菜品供应不足时，系统根据规则自动分配有效份数。

### 2.3 空间创建者 owner

空间创建者是空间的管理者。

权限：

- 拥有普通成员的全部权限。
- 设置成员角色，例如指定某个成员为厨师。
- 管理空间基础信息。
- 后续可扩展为空间成员移除、邀请方式管理、空间配置管理等。

## 3. 核心概念

### 3.1 空间 Space

空间是数据隔离的基本单位。一个用户可以加入多个空间，不同空间之间的菜品、点单局、订单和成员互不影响。

示例：

- 我家饭局空间。
- 朋友聚餐空间。
- 其他用户自己的独立空间。

### 3.2 菜品 Dish

菜品属于某个空间，由空间成员上传。

菜品包含：

- 菜名。
- 图片。
- 虚拟价格。
- 食材。
- 做法描述。
- 上传者。
- 创建时间。
- 是否启用。

### 3.3 点单局 Menu Session

点单局表示一次共享点单，例如“周六晚饭”“本周聚餐”“春节菜单”。

一个空间可以同时存在多个点单局。成员进入空间后，可以选择进入某个点单局并共同添加菜品。

### 3.4 菜品添加记录 Menu Item Entry

菜品添加记录表示某个用户在某个点单局里添加了某道菜若干份。

底层需要保留添加批次和时间，用于后续供应不足时按先后顺序自动分配有效份数。

示例：

```text
A 在 19:00 添加可乐鸡翅 2 份
B 在 19:03 添加可乐鸡翅 1 份
```

展示时合并为：

```text
可乐鸡翅 x3
A x2，B x1
```

### 3.5 厨师确认 Chef Confirmation

厨师确认表示某道菜在某个点单局中的实际供应情况。

确认状态：

- `available`：可做，实际可做份数等于原始点单总份数。
- `partial`：部分可做，需要填写实际可做份数。
- `unavailable`：无货，实际可做份数为 0。

### 3.6 订单 Order

点单局提交后生成订单。点单局允许后续继续修改和重新提交，因此订单需要支持版本。

### 3.7 订单版本 Order Version

每次提交或重新提交都会生成一个订单版本，用于记录当时的菜单、厨师确认、有效份数和金额快照。

## 4. MVP 功能范围

第一阶段只做最小可用版本，目标是让自己和朋友能真实使用。

包含功能：

- 微信登录。
- 创建空间。
- 加入空间。
- 空间成员列表。
- 指定厨师。
- 上传菜品。
- 浏览菜品。
- 创建多个点单局。
- 往点单局添加菜品。
- 同一道菜按总份数合并展示。
- 显示每个用户对每道菜的点单份数。
- 普通成员只能修改自己的份数。
- 提交点单局。
- 厨师确认可做、部分可做、无货。
- 供应不足时自动分配有效份数。
- 显示最终有效汇总。
- 重新提交订单版本。
- 小程序内通知或提醒菜单发生变化。

暂不包含：

- 微信支付。
- 真实配送。
- 商家入驻审核。
- 复杂财务结算。
- 多端 Web 或 App。
- 高级营销功能。

## 6. 主要业务流程

### 6.1 创建空间流程

```text
用户登录
  -> 创建空间
  -> 成为 owner
  -> 邀请朋友加入
  -> 指定一个或多个 chef
```

### 6.2 上传菜品流程

```text
成员进入空间
  -> 打开菜品库
  -> 新增菜品
  -> 上传图片
  -> 填写菜名、价格、食材、做法
  -> 保存到空间菜品库
```

### 6.3 点单流程

```text
成员创建点单局
  -> 其他成员进入同一个点单局
  -> 成员从菜品库选择菜品
  -> 添加自己的份数
  -> 系统合并同一道菜的总份数
  -> 显示每个用户的份数明细
  -> 某个成员提交点单局
```

### 6.4 厨师确认流程

```text
点单局提交
  -> 状态变为待厨师确认
  -> 厨师打开确认页
  -> 对每道菜标记可做、部分可做或无货
  -> 系统计算有效份数
  -> 系统计算最终汇总
  -> 成员查看最终结果
```

### 6.5 重新提交流程

```text
成员继续添加或修改自己的菜品
  -> 点单局标记为有变更
  -> 成员重新提交
  -> 生成新的订单版本
  -> 厨师重新确认或沿用部分确认结果
  -> 系统通知成员菜单已更新
```

## 7. 权限规则

### 7.1 空间权限

- 用户必须是空间成员，才能查看空间数据。
- 所有业务数据都必须带有 `space_id`。
- 查询时必须校验用户是否属于该空间。

### 7.2 菜品权限

- 所有空间成员都可以上传菜品。
- 第一阶段建议只允许上传者编辑或删除自己的菜品。
- owner 后续可拥有管理所有菜品的权限。

### 7.3 点单权限

- 所有空间成员都可以创建点单局。
- 所有空间成员都可以向点单局添加菜品。
- 普通成员只能修改或删除自己的添加记录。
- 点单局提交后仍允许继续追加或修改。

### 7.4 厨师确认权限

- 只有 chef 和 owner 可以修改厨师确认结果。
- 厨师确认只影响实际可做份数，不直接改写用户原始点单记录。

## 8. 菜品与点单规则

### 8.1 同菜品合并展示

同一个点单局中，同一道菜只显示一行。

示例：

```text
番茄炒蛋 x3    12 饭票/份
A x2，B x1
```

### 8.2 用户份数明细

系统需要显示每个用户对该菜的点单份数。

示例：

```text
可乐鸡翅 x4
A x2，B x1，C x1
```

### 8.3 用户修改规则

普通成员只能修改自己的份数。

例如：

```text
A x2，B x1
```

A 只能修改 A 的 2 份，不能修改 B 的 1 份。

### 8.4 添加记录批次

底层应按添加批次存储，而不是只存最终用户数量。

原因：

- 需要记录谁先点。
- 厨师供应不足时要按时间顺序分配有效份数。
- 后续可追踪点单变化。

## 9. 厨师确认规则

### 9.1 可做

当厨师标记菜品可做时，有效份数等于原始点单总份数。

示例：

```text
番茄炒蛋 原点 x3
厨师确认：可做
最终有效 x3
```

### 9.2 部分可做

当厨师标记只能做 N 份时，系统按点单时间顺序自动分配有效份数。

规则：

- 先添加者优先。
- 同一批次添加多份时，按该批次数量依次占用可做额度。
- 如果剩余额度不足，则该批次只保留可覆盖的份数。
- 后添加且没有剩余额度的记录，有效份数为 0。

示例一：

```text
原始点单：
A 19:00 添加 2 份
B 19:03 添加 1 份

厨师确认只能做 1 份

最终分配：
A 有效 1 份
B 有效 0 份
```

示例二：

```text
原始点单：
A 19:00 添加 1 份
B 19:03 添加 2 份

厨师确认只能做 2 份

最终分配：
A 有效 1 份
B 有效 1 份
```

### 9.3 无货

当厨师标记无货时，有效份数为 0。

展示建议：

```text
红烧鱼 x1    30 饭票/份
A x1
厨师确认：无货
最终有效 x0
```

界面中可将菜名或原份数显示为删除线。

## 10. 汇总与金额计算规则

### 10.1 原始汇总

原始汇总按成员原始点单计算。

包含：

- 原始总份数。
- 原始总金额。
- 每个成员原始份数。
- 每个成员原始金额。

### 10.2 最终汇总

最终汇总按厨师确认后的有效份数计算。

包含：

- 最终有效总份数。
- 最终有效总金额。
- 每个成员最终有效份数。
- 每个成员最终有效金额。

### 10.3 价格快照

提交订单版本时，需要保存菜品名称、图片、价格等快照。

原因：

- 后续菜品价格修改后，不应影响历史订单。
- 历史订单需要保持当时的真实结果。

### 10.4 计算示例

原始点单：

```text
番茄炒蛋 x3    12 饭票/份
A x2，B x1

可乐鸡翅 x3    20 饭票/份
A x2，B x1
厨师确认只能做 x1
最终分配：A x1，B x0
```

原始汇总：

```text
总份数：6 份
总金额：96 饭票
A：4 份，64 饭票
B：2 份，32 饭票
```

最终汇总：

```text
总有效份数：4 份
总有效金额：56 饭票
A：3 份，44 饭票
B：1 份，12 饭票
```

## 14. 少货自动分配算法

输入：

- 某道菜的所有有效添加记录。
- 厨师确认可做份数 `available_quantity`。

步骤：

```text
1. 按 created_at 从早到晚排序。
2. remaining = available_quantity。
3. 遍历添加记录。
4. 如果 remaining <= 0，该记录有效份数为 0。
5. 如果 remaining >= entry.quantity，该记录有效份数为 entry.quantity。
6. 如果 remaining < entry.quantity，该记录有效份数为 remaining。
7. 每次分配后扣减 remaining。
8. 按 user_id 汇总每个用户的有效份数。
```

输出：

- 每个用户对该菜的有效份数。
- 该菜最终有效总份数。
- 该菜最终有效金额。

## 15. 技术方案建议

第一阶段推荐：

```text
微信小程序原生 + 微信云开发 CloudBase
```

原因：

- 快速启动。
- 适合微信生态。
- 微信登录、云数据库、云存储、云函数集成方便。
- 不需要第一阶段维护独立服务器。
- 适合小范围试用。

后续如果用户规模扩大，可以考虑：

- 自建 Node.js/NestJS 后端。
- PostgreSQL 或 MySQL 数据库。
- 对象存储保存图片。
- 独立管理后台。
- Web 端或 App 端。

## 17. 第一阶段开发顺序

建议按以下顺序开发：

```text
1. 初始化微信小程序项目和云开发环境。
2. 完成微信登录和 users 集合。
3. 完成空间创建、加入和成员角色。
4. 完成菜品库和图片上传。
5. 完成点单局创建。
6. 完成菜品加入点单局。
7. 完成同菜品合并展示和用户份数明细。
8. 完成普通成员只能修改自己份数的权限。
9. 完成点单局提交和订单版本。
10. 完成厨师确认。
11. 完成少货自动分配算法。
12. 完成原始汇总和最终汇总。
13. 完成小程序内通知。
14. 做一次完整试用和问题修正。
```

## 18. 待确认问题

以下问题可以在后续开发前继续确认：

- 空间加入方式使用邀请码、二维码，还是两者都要。
- 虚拟货币名称是否每个空间可以自定义。
- 菜品是否允许其他成员编辑。
- 点单局是否需要截止时间。
- 厨师确认后是否允许普通成员继续修改。
- 订单最终是否需要关闭状态，关闭后禁止继续修改。
- 是否需要菜品分类和搜索。
- 第一版是否接入微信订阅消息。
